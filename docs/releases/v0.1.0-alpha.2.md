# v0.1.0-alpha.2

## Date

2026-05-03

## Highlights

- Module/API foundation expanded across customer, rate, billing, reporting,
  invoice, payment, provider, agent, admin configuration, and telephony
  workflows.
- VectaVoIP provider flow now includes registration/status retry handling,
  rollback-safe default provisioning, credential rotation, signed webhooks,
  rate preview/import, DID inventory, and production-compatible local API
  smoke checks.
- API coverage now includes customers, balances, rates, tariff plans/groups,
  packages, CDRs, reports, payments, invoices, receipts, providers, DIDs,
  trunks, SIP/IAX accounts, PJSIP provisioning, agents, and safe admin settings.
- PJSIP provisioning now supports customer devices and trunks plus endpoint
  list/detail/update responses that do not expose auth passwords.
- Legacy direct-card callback payloads are blocked by default and payment
  callback logs redact card/security-code fields.
- Invoice detail responses include module-backed tax summaries from
  `cc_invoice_item`.
- Docker sandbox backup/restore was verified end to end.
- Known A2Billing security advisory coverage is documented in
  `docs/security-patch-matrix.md`.

## Upgrade Notes

- This remains an alpha build for sandbox/operator validation.
- Keep legacy admin, customer, and agent portals behind trusted network controls.
- Do not enable contrib payment gateways or legacy direct-card flows in
  production.
- Use hosted/tokenized payment provider flows only.
- Run migrations and provider imports in dry-run mode before applying changes to
  any real database.

## Database Migrations

- Provider import log and provider webhook event log.
- VectaVoIP installation and DID inventory records.
- A2BillingPlus audit log.
- PJSIP realtime tables and endpoint mapping table.

## Provider Changes

- VectaVoIP remains the first-class provider module.
- Registration/status clients have retry coverage.
- Default provider provisioning is transaction-backed with rollback tests.
- Production-compatible registration, status, and rate preview smoke checks pass
  locally.

## Payment Changes

- Stripe payment intent and webhook module foundations are present.
- Customer payment portal API exposes hosted payment entry, payment history, and
  receipt/invoice references.
- Legacy direct-card callbacks are disabled by default unless
  `A2BP_FEATURE_LEGACY_DIRECT_CARD_FLOW` is explicitly enabled.

## Security Notes

- New module APIs use service-key/customer/agent authentication boundaries as
  appropriate and avoid returning SIP/PJSIP/card secrets.
- Sensitive or balance-impacting module changes emit audit events.
- Legacy UI surfaces remain compatibility surfaces and are not considered
  production-hardened.
- Known public A2Billing advisory coverage is tracked in
  `docs/security-patch-matrix.md`.

## Beta Blockers

- Run Stripe webhook verification against a real Stripe sandbox fixture and
  record exact command/output.
- Test migration apply against a sanitized legacy snapshot, not only dry-run
  migration.
- Run and document an Asterisk 20 or 22 PJSIP sandbox call path.
- Decide which module-backed workflows are ready for UI replacement and keep
  payment/telephony UI gates blocked until the live sandbox checks above pass.

## Known Alpha Limitations

- Legacy portals are still present and should be treated as compatibility UI.
- Payment UI replacement is blocked until hosted sandbox payment and webhook
  verification pass.
- Trunk, SIP/PJSIP, and DID UI replacement is blocked until Asterisk 20/22
  call-path verification passes.
- Migration apply is not yet validated against a sanitized real legacy dataset.
- WebRTC remains deferred until SIP/PJSIP flows are stable.
